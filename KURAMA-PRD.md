# Kurama — Product Requirements Document

**Status:** Draft for product review
**Updated:** 21 November 2026
**Product:** Kurama, a personal computer-control assistant

## 1. Summary

Kurama is an agentic personal assistant that lets its owner control their computer through either typed text or spoken commands. It understands an intent, chooses and uses available computer tools, checks the result, and reports what it did. It should work across the user’s files, applications, and browser rather than depend on a catalog of hard-coded workflows.

Voice and text are both first-release modes. Voice uses speech-to-text (STT), the same agent and tools as text mode, and text-to-speech (TTS) for spoken replies. Sarvam provides the initial cloud AI services; computer actions execute locally on the user’s machine.

## 2. Problem and goal

People should be able to ask Kurama for outcomes in ordinary language—such as “open WhatsApp and search for the latest message from Maya” or “find the PDF I downloaded yesterday and summarize it”—without navigating every step themselves.

**Goal:** Make a capable, understandable assistant that can take multi-step actions across the computer, in both text and voice, while keeping the owner in control of consequential changes.

**Not the goal:** Ship a collection of fixed macros, a phone-call agent, or a cloud service that remotely controls the computer.

## 3. Users and core experience

**Primary user:** The owner of one personal computer, comfortable giving natural-language instructions but not necessarily writing scripts or configuring automation.

**Interaction loop:**

1. The user types a request or speaks using the microphone.
2. Kurama shows the recognized request (voice mode) and a brief plan when a task has multiple steps or meaningful effects.
3. The agent selects tools, acts locally, and checks observable results.
4. Before a consequential action, Kurama presents the specific action and asks for confirmation.
5. Kurama reports completion, partial completion, or the reason it stopped. The user can interrupt voice playback or cancel an active task.

Text and voice use the same conversation, permissions, agent, and action rules. The user can switch modes at any time.

## 4. Product principles

- **Outcome-oriented:** The user describes what they want; Kurama decides the steps and tools.
- **Broad capability, bounded authority:** Capabilities are extensible across the computer, while each action is checked against explicit permissions and confirmation rules.
- **Observe and verify:** Kurama checks that an action happened before claiming success.
- **Owner remains in control:** Ask before irreversible, external, privacy-sensitive, or security-sensitive actions.
- **Visible and interruptible:** Show activity, allow stop/cancel, and make it clear when the microphone is active.
- **Local execution:** Files and desktop actions run on the user’s computer. Cloud AI receives only the information needed for the request.

## 5. Scope

### First release

- A desktop interface with text input and voice input/output.
- Push-to-talk voice capture, visible transcript, and spoken response. Continuous listening or a wake word is not required for the first release.
- General agent loop: understand request, plan, call tools, inspect results, recover from ordinary failures, and summarize.
- Computer capabilities exposed through tools, including:
  - Inspect and search accessible files and folders; read supported text and document formats.
  - Create, move, rename, and edit files; show a preview and ask before overwrite or deletion.
  - Find and launch installed applications; interact with supported application UI.
  - Use a browser to navigate, search, read pages, and perform supported interactions.
  - Manage windows, clipboard, and basic desktop state where the OS permits.
- A permission and confirmation layer shared by text and voice.
- A local activity history with request, actions, confirmation outcome, and result; redact secrets and sensitive content.
- Clear handling for unavailable apps, unsupported content, permission errors, network failures, and ambiguous requests.

### Out of scope for the first release

- Phone-call control, multi-user/team accounts, remote administration, and unattended background task scheduling.
- Continuous microphone listening or always-on wake word.
- Silent execution of arbitrary shell commands generated by the model.
- Guaranteed control of every third-party app. Unsupported or inaccessible apps must be reported clearly.
- Autonomous financial transactions, account/security changes, bulk deletion, or sending messages without the owner’s confirmation.

## 6. Functional requirements

### FR-1: Text and voice input

- Accept typed natural-language requests.
- Accept spoken requests through push-to-talk and display the transcript before execution when practical.
- Let the user correct a transcript or cancel before the agent acts.
- Support English initially; keep language selection extensible. Add Indian-language and code-mixed support where Sarvam’s selected STT model supports it.

### FR-2: Agentic task execution

- Handle requests as goals, not fixed command phrases.
- For multi-step work, form a plan, choose tools dynamically, and adapt to observed outcomes.
- Keep the user updated during long tasks and allow cancellation.
- Treat content from web pages, files, and app screens as untrusted data, never as authority to change Kurama’s rules or permissions.
- Ask a concise clarifying question when key details are missing or a target cannot be distinguished safely.

### FR-3: Computer tools

- Provide a tool interface for filesystem, application, browser, and desktop operations.
- Run tools locally and return structured success/error results to the agent.
- Limit tools to explicit operations and validated arguments. Do not expose an unrestricted shell to the model.
- Verify results through available UI state, filesystem state, or application response before reporting success.
- Start with Ubuntu 24.04 as the initial desktop target; keep OS-specific tools behind an adapter so other platforms can be added later.

### FR-4: Confirmation and permissions

Kurama may perform low-risk, reversible actions without pausing when they are clearly requested. It must ask for confirmation immediately before:

- Sending or publishing messages, emails, posts, or other content.
- Deleting files, overwriting existing data, or making broad/bulk changes.
- Installing software, changing security settings, permissions, startup behavior, or system configuration.
- Sharing private data externally, submitting forms, making purchases, or taking other actions with external consequences.

The confirmation must name the target and action, and show content or scope where feasible. Approval applies only to the shown action and scope. Voice approval must be explicit and unambiguous; silence or uncertain recognition is not approval. The user can always cancel.

### FR-5: Speech output

- Speak concise responses and progress updates in voice mode.
- Allow interruption and provide the same result in text.
- Do not speak sensitive file contents or credentials aloud unless the user explicitly asks.

### FR-6: Privacy, credentials, and history

- Keep API keys outside source code and version control.
- Make clear that STT, LLM, and TTS requests use Sarvam’s cloud APIs and may send audio, transcripts, or generated text as required by those APIs.
- Do not upload files or full screen contents by default; send only a relevant excerpt or the minimum context needed for the task.
- Store settings and activity locally. Provide controls to clear local history and configure retention.
- Redact API keys, passwords, tokens, and similarly sensitive values from logs and model context where possible.

## 7. Initial technical direction

- **Reuse before building:** Do not implement an agent loop or desktop-control stack from scratch. First evaluate Hermes Agent with the `computer-use-linux` MCP server on the target Ubuntu 24.04 GNOME Wayland session. Hermes provides the tool-using agent and text/voice interaction; `computer-use-linux` provides Linux-native accessibility-aware observation and input. Confirm target-version compatibility and remaining gaps before committing to a fork or integration.
- **Alternative desktop tool layer:** OpenDesk is another Linux computer-use MCP server worth comparing. Chatuse is another MIT-licensed tool server, but its stated baseline is Ubuntu 24.04 GNOME on Xorg, with Wayland marked experimental.
- **Alternative full application:** Assess Personal Jarvis if a ready-made voice/text desktop app is preferable to building Kurama’s interface. It publishes Linux AppImage and describes browser/desktop tools and approvals. Verify its model-provider flexibility, Ubuntu 24.04 Wayland behavior, and branding/customization before adopting it.
- **Sarvam LLM:** Configure the selected harness to use Sarvam Chat Completions V2 (`https://api.sarvam.ai/v2`) and verify tool-call interoperability with `glm5.3` and `glm5.3-flash`. Sarvam documents these as serverless models and supports tool calling on its chat models.
- **Sarvam speech:** If the chosen harness has no native Sarvam audio provider, add only thin STT/TTS provider adapters using the Sarvam SDK. Evaluate realtime STT (`saaras:v3-realtime` or `saaras:v4`) and streaming TTS (`bulbul:v4-flash`); keep the harness’s existing voice/UI path wherever it fits.
- **Secrets:** Keep `SARVAM_API_KEY` in the selected harness’s secret store or environment-backed local configuration. Never put it in source code, prompts, logs, screenshots, or commits.
- **Action safety:** Prefer the chosen harness’s approval and permission gates, then verify they meet this PRD. Keep any missing policy checks outside the LLM; only validated, permitted tool calls may execute.

This direction is a reuse-first hypothesis, not a final stack decision. The initial spike should test typed and spoken requests, a browser search, opening a desktop app, a confirmation-gated write action, interruption/cancel, and observed-result verification on the target machine. Recheck model availability, APIs, licenses, and pricing before adoption.

- A local Python HTTP app now serves a text chat UI at `http://127.0.0.1:8765`, calls Sarvam Chat Completions V2 with `glm5.3-flash`, and executes model-selected calls through bounded tools for installed apps, websites/search, and filename-based file operations. It starts the upstream `computer-use-linux` 0.7.59 MCP server and exposes its read-only app/window/accessibility observations after verifying their MCP read-only annotations.
- Push-to-talk recording posts audio through the local server to Saaras V4, displays an editable transcript, and uses the same chat path as typed requests. Optional replies use Bulbul V4 Flash. A generated speech clip was transcribed through the prototype endpoints successfully.
- The text loop was verified end-to-end: Sarvam selected `open_app` for Calculator, the tool reported success, and the Calculator process was observed running. The browser UI also submitted this command and displayed the reply. A direct `computer-use-linux` MCP probe listed accessible apps and read Calculator's accessibility tree; GNOME window listing still fails because the extension has not loaded in this login session.
- The API key was copied from the provided reference `.env` into the project `.env`; `.env` is Git-ignored and has mode `0600`. The key is never returned by the health endpoint.
- This is a narrow prototype, not the complete PRD: app controls launch apps and inspect accessibility text. The browser showed/canceled a pending click, then the user approved one exact Calculator click; the normal and background AT-SPI action paths both refused input because GNOME has not loaded the installed extension's WindowControl D-Bus service. No click was sent. The app now reports a fresh-login requirement instead of suggesting setup again. Screenshots, file content reading, confirmations for actions outside desktop input, persistent history, and real microphone capture in a browser are not yet verified. The server binds to localhost and has no authentication.

## 8. Quality requirements

- **Safety:** No consequential action executes without the required confirmation. Prompt injection in a page or file cannot bypass local policy.
- **Correctness:** Kurama distinguishes completed, failed, and partially completed tasks and does not claim unverified success.
- **Responsiveness:** Show immediate acknowledgement; stream partial STT/LLM/TTS output when supported. Measure end-to-end voice latency on the target computer.
- **Resilience:** A failed model/API request or unavailable app must stop safely, preserve the conversation, and explain the next useful step.
- **Privacy:** No always-on audio capture in the first release. Show microphone state and give the user a clear stop control.
- **Maintainability:** Add capabilities through separately testable tools and OS adapters, not by growing one monolithic prompt or a fixed workflow list.

## 9. Success criteria

The first release is ready for a small personal-use trial when:

- A user can complete an ordinary task through text and through voice using the same agent and tools.
- A multi-step request can combine at least two computer areas (for example, browser plus files) and Kurama verifies its result.
- All listed consequential actions request specific confirmation, and refusal/cancel stops the action.
- The user can interrupt voice playback and cancel a running task.
- Kurama handles ambiguous targets by asking instead of guessing when a wrong choice could have meaningful consequences.
- The user can inspect and clear local activity history.
- No API key or secret appears in tracked source, normal logs, or the activity view.

## 10. Risks and open decisions

- **App compatibility:** Apps expose different automation interfaces; prioritize accessibility/UI automation and report unsupported cases rather than promising universal control.
- **Model reliability:** Tool selection can be incorrect. Keep validation, confirmation, and execution policy deterministic and test against a task set before enabling wider permissions.
- **Cloud privacy and cost:** Voice and LLM calls consume credits and send request data to Sarvam. Measure per-task usage and show a usage estimate or meter before broad rollout.
- **Speech recognition errors:** Display transcripts and require confirmation for consequential actions so misheard names, recipients, or paths do not trigger them.
- **Display session:** Ubuntu 24.04 is the target; confirm GNOME Wayland desktop-control support in candidate harnesses. Wayland has different capture and input permissions and may refuse some background actions.
- **Harness selection:** Choose between extending Hermes Agent with `computer-use-linux`, using a different full desktop app such as Personal Jarvis, or combining a small Kurama interface with an MCP computer-use server.
- **Language and voice:** Confirm launch languages, preferred voice, and whether translated/code-mixed interactions are required.
- **Interaction surface:** Select the desktop UI framework and decide whether Kurama lives in a normal window, system tray, or both during technical design.
